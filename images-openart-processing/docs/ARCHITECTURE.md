# Architecture

The Electron main process owns filesystem access, SQLite, provider calls, the bounded `p-queue`, retry policy, atomic downloads, and report generation. The React renderer receives plain data through a context-isolated preload bridge and cannot access Node APIs.

The pipeline is: `scan -> local Validate Batch -> confirmation modal -> persist run/job -> queue -> upload cache -> generate -> poll -> atomic raw download -> finalise -> SQLite/report`. Validate Batch never uploads or creates provider work. The first Generate Selected click only opens the modal. Only the modal's Generate Images handler can start a run.

The standard renderer workflow uses the read-only `resources/presets/entitled-v1` bundle. It loads ten numbered prompt cards, four configured presentation references, and the permanent garment-authority rules without asking the user to browse for prompt or presentation files. Product scans treat every supported image in each immediate SKU folder as a product source, sort naturally, and create one job per selected prompt. Prompt 10 is deliberately disabled until its separate size-chart dependencies are supplied. The older manual fidelity preflight IPC remains diagnostic-only and is not shown on the main dashboard.

`OpenArtCliProvider` is the sole production path. `MockOpenArtProvider` and the fake CLI are test-only. The official executable owns OAuth and token refresh. MCP remains experimental and is not exposed in the production UI because Codex and Electron are separate clients. The CLI adapter only uses observed structured JSON output and refuses to invent unsupported generation flags.

SQLite schema version 10 stores normalized run, job-input, and job-event records alongside legacy job history, UUID job IDs, immutable prompt/input snapshots, lifecycle statuses, separate attempt/retry counts, generation IDs, settings, uploaded asset metadata, and raw/final output paths. Image bytes never enter SQLite. WAL mode supports safe local persistence, and startup IPC rehydrates completed, failed, and incomplete jobs. Incomplete jobs with a persisted creation ID resume polling rather than resubmitting; an ambiguous submitting job without a creation ID is failed safely and is never resubmitted automatically. The renderer verifies output existence and marks missing files. Raw provider output is preserved; final output is produced as a validated 1254×1254 PNG derivative. Current runs are separated from collapsed historical runs.

Real jobs require a user-selected writable durable output directory. Temporary directories such as `/tmp` are accepted only for mock/test execution. The last output directory is stored in the Electron user-data preferences file. If decoding or finalisation fails, the raw result remains available and the job is not regenerated automatically.
